# PORTING.md — порядок переходу на `open-cpu` з інших репозиторіїв

Порядок міграції, що дозволяє зібрати в `open-cpu` код виявлення можливостей
CPU та код операцій GF(2^8), які окремо є в `open-raid-z` / `aruaru-db` /
`aruaru-llm` / `open-cuda` тощо.

## 0. Передумови

`open-cpu` — це **бібліотечний крейт**, а не резидентний сервіс. Міжпроцесна
взаємодія та запуск окремого процесу не потрібні: усе зводиться до додавання
залежності в `Cargo.toml` і виклику функцій.

## 1. Додавання залежності

Під локальним робочим диском `F:\runo` найпростіша path-залежність:

```toml
[dependencies]
open-cpu = { path = "../open-cpu" }
```

При використанні з крейта-учасника робочого простору бажано написати в
`Cargo.toml` кореня робочого простору

```toml
[workspace.dependencies]
open-cpu = { path = "../open-cpu" }
```

і вказати на стороні учасника `open-cpu = { workspace = true }`.

При майбутньому переході на git-залежність:

```toml
open-cpu = { git = "https://github.com/aon-co-jp/open-cpu", branch = "main" }
```

Ім'я крейта — з дефісом, `open-cpu`; шлях для звернення з Rust — з
підкресленням, `open_cpu`.

## 2. Заміна коду виявлення можливостей CPU

До міграції (типовий для репозиторіїв шаблон):

```rust
static HAS_AVX2: OnceLock<bool> = OnceLock::new();
fn has_avx2() -> bool {
    *HAS_AVX2.get_or_init(|| is_x86_feature_detected!("avx2"))
}
```

Після міграції:

```rust
if open_cpu::detect().avx2 { /* ... */ }
```

`detect()` усередині вже кешовано через `OnceLock`, тож кешувати додатково на
стороні виклику не потрібно. Оскільки повертається
`&'static CpuCapabilities`, алокація теж не відбувається.

Доступні поля: `avx2` `avx512f` `avx512bw` `avx512vl` `pclmulqdq`
`bmi1` `bmi2` `fma` `aes` `popcnt` `sha` `sse2` `ssse3` `avx_vnni` `avx512vnni`.

## 3. Заміна операцій GF(2^8) / розрахунку парності (переважно `open-raid-z`)

Незвідний многочлен у `open-cpu` — `0x11d`, твірний елемент — `g = 2`, що
збігається з Linux md/RAID6 та ZFS RAID-Z. **Перед міграцією обов'язково
перевірте, чи збігаються з цим многочлен і твірний елемент у вашому
репозиторії.** Якщо вони відрізняються, числові значення перестануть сходитися.

| Типова форма до міграції | Після міграції |
|---|---|
| `for i in .. { p[i] ^= d[i] }` | `open_cpu::gf_xor(&mut p, &d)` |
| `for i in .. { q[i] ^= gf_mul(d[i], c) }` | `open_cpu::gf_mul_parity(&mut q, &d, c)` |
| `for i in .. { acc[i] = mul2(acc[i]) ^ d[i] }` | `open_cpu::gf_mul2_xor(&mut acc, &d)` |
| `for i in .. { acc[i] = mul4(acc[i]) ^ d[i] }` | `open_cpu::gf_mul4_xor(&mut acc, &d)` |
| Метод Горнера з довільною кількістю `×2^n` | `open_cpu::gf_mul_pow2_xor(&mut acc, &d, n)` |
| Власна `gf_mul(a: u8, b: u8) -> u8` | `open_cpu::gf_mul(a, b)` (`const fn`) |
| Власна `mul2_byte(b) -> u8` | `open_cpu::gf_mul2_byte(b)` (`const fn`) |
| Власний розрахунок коефіцієнта `g^i` | `open_cpu::raid6_coeff(i)` |
| Пакетний розрахунок P/Q | `open_cpu::raid6_parity(&stripes, &mut p, &mut q)` |
| Пакетний розрахунок P/Q/R (відповідає RAID-Z3) | `open_cpu::raid6_parity3(&stripes, &mut p, &mut q, &mut r)` |

`gf_mul_parity` / `gf_xor` викликають panic за `dst.len() != src.len()`.
Вирівнюйте довжину страйпів на стороні виклику.

Якщо потрібно явно викликати конкретну реалізацію (для бенчмарків або
перевірки):

- `open_cpu::gf_mul_parity_scalar(...)` / `gf_xor_scalar(...)` /
  `gf_mul_pow2_xor_scalar(...)` — safe
- `unsafe { open_cpu::gf_mul_parity_avx2(...) }` — сторона, що викликає,
  гарантує підтримку AVX2
- `unsafe { open_cpu::gf_mul_parity_pclmul(...) }` — те саме для SSSE3+PCLMULQDQ
- `unsafe { open_cpu::gf_mul_parity_avx512(...) }` — **виконання не перевірено**

## 4. Перевірка після міграції (обов'язково)

1. `cargo build` — розв'язання залежностей і збірка мають проходити.
2. `cargo test` — **усі наявні тести мають проходити**. Зокрема, переконайтеся,
   що байтові послідовності парності до і після заміни повністю збігаються.
   Якщо в наявних тестах немає порівняння значень парності, додайте його під
   час міграції.
3. Якщо виводити в журнал один рядок `open_cpu::runtime_summary()`, то згодом
   можна буде дізнатися, яку реалізацію було обрано на реальній машині.

## 4.5 Реальний приклад міграції (`open-raid-z`, 2026-08-22)

Для довідки наведемо ключові моменти першого реального випадку міграції:

- `std::is_x86_feature_detected!` усередині `detect_level()` замінено на
  звернення до `open_cpu::detect()` (специфічне для репозиторію перерахування
  `SimdLevel` залишено як є, до open-cpu перенесено **лише вихідні дані для
  його визначення**). Завдяки цьому наявні сторони виклику не довелося
  змінювати взагалі.
- У `gf_mul_xor_into()` / `xor_into()` / `mul_pow2_xor_into()` до open-cpu
  делеговано **лише шлях AVX2**, а шлях AVX-512 (в open-cpu він теж не
  перевірений) і шлях SSE2 (в open-cpu реалізації немає) залишено з
  реалізацією на стороні репозиторію. Рішення ухвалено за принципом **не
  виконувати заміну, що знижує продуктивність**.
- SIMD-ядра, що перестали використовуватися, не видалено, а залишено з
  позначкою `#[allow(dead_code)]` як еталон для майбутньої взаємної перевірки
  зі стороною open-cpu.

Рекомендується саме такий підхід: «не замінювати все одразу, а поетапно
делегувати починаючи з тих частин, які еквівалентні й не втрачають у
продуктивності».

## 5. Зауваження

- **Шлях AVX-512 не перевірено виконанням** (на машині розробки його немає).
  За замовчуванням він не обирається, тож міграція не змінить поведінку.
  Задавайте `OPEN_CPU_ENABLE_AVX512=1` лише під час перевірки на машині з
  AVX-512.
- POPCNT/BMI/FMA/AES-NI/SHA-NI/VNNI — **лише виявлення**. Реалізацій
  контрольних сум, стиснення та матричних операцій з їх використанням у
  `open-cpu` ще немає, тож відповідний код на стороні `aruaru-db` /
  `aruaru-llm` поки мігрувати не можна (перенести заздалегідь лише частину з
  виявленням можливо).
- Поза x86 (ARM тощо) усі можливості стають `false` і відбувається відкат до
  скалярної реалізації. Крос-збірка проходить, але оптимізації на кшталт NEON
  не підтримуються.
