# Політика розробки та правила середовища розробки (open-cpu)

Цей репозиторій — частина екосистеми `aon-co-jp`. **Нормативним джерелом для
спільних для всіх репозиторіїв принципів проєктування та правил експлуатації
(ретельна перевірка, заборона перебільшених звітів, відмова від винаходження
велосипеда, автоматичне продовження без запиту підтвердження тощо) є
[`open-raid-z/CLAUDE.md`](https://github.com/aon-co-jp/open-raid-z/blob/main/CLAUDE.md).**
Тут вони не дублюються; описано лише питання, специфічні для цього репозиторію.

Робочий диск — `F:\runo\open-cpu` (нове компонування).

## Роль цього репозиторію

Створений як спільна основа, тому що `open-raid-z` / `aruaru-db` / `aruaru-llm` /
`open-cuda` збиралися **кожен по-своєму** реалізовувати виявлення під час
виконання та диспетчеризацію наборів інструкцій CPU
(AVX2/AVX-512/PCLMULQDQ/BMI1/BMI2/FMA3/AES-NI/POPCNT/SHA-NI).

- **Це бібліотечний крейт** (вказівка користувача, 2026-08-22). Він не має
  ставати резидентним сервісом (демоном). Кожен репозиторій додає його до
  `[dependencies]` і лінкує всередину того самого процесу. Не запроваджувати
  міжпроцесну взаємодію.
- Область дії обмежена «виявленням можливостей CPU» та «диспетчеризацією
  обчислень на основі результату цього виявлення». Не переносити сюди доменну
  логіку окремих репозиторіїв (стратегію чергування в RAID, керування
  сторінками в БД, завантаження моделей в LLM тощо).
- Не збільшувати кількість залежних крейтів (наразі `[dependencies]` порожній,
  лише `std`). Це основа, що лежить у самому низу кожного репозиторію, тож
  привнесена залежність пошириться на все.

## Правила реалізації та перевірки (специфічні для цього репозиторію)

- **Додавши SIMD-реалізацію, обов'язково одночасно пишіть тест на збіг виходу
  зі скалярною реалізацією.** Обов'язково включайте до тест-кейсів залишок
  (довжину, не кратну ширині вектора).
- **Шляхи коду, які неможливо виконати на реальній машині, явно позначайте як
  «не перевірено» і не дозволяйте обирати їх диспетчеризацією за
  замовчуванням.** Наразі це стосується шляху AVX-512 (машина розробки
  AMD Ryzen 9 3950X не має AVX-512). Він вмикається лише за opt-in через
  `OPEN_CPU_ENABLE_AVX512=1`. Коли перевірку на машині з AVX-512 буде
  завершено, зніміть це обмеження та оновіть позначки «не перевірено» в
  README.md / PORTING.md / цьому файлі.
- Записуючи числа бенчмарків, пишіть «виміряно» **лише про те, що було
  справді виміряно**. Не видавайте оцінкові та теоретичні значення за
  виміряні.
- `cargo bench` не використовується; достатньо простого вимірювання через
  `std::time::Instant` у `examples/bench.rs` (щоб не збільшувати кількість
  залежностей).

## HANDOFF

- **2026-08-22 створення з нуля + інтеграція у 2 репозиторії**:
  початкову реалізацію створено зі стану порожнього репозиторію.
  - `src/caps.rs`: структура `CpuCapabilities` та `detect()` (кеш `OnceLock`).
    Об'єкти виявлення: avx2 / avx512f / avx512bw / avx512vl / pclmulqdq /
    bmi1 / bmi2 / fma / aes / popcnt / sha / sse2 / ssse3 / avx-vnni /
    avx512vnni.
  - `src/gf.rs`: операції GF(2^8) для RAID6 (многочлен 0x11d, твірний елемент
    g=2). Публікуються `gf_xor` / `gf_mul_parity` / `raid6_parity` /
    `raid6_coeff`, диспетчеризація під час виконання між 4 реалізаціями:
    скалярною / PCLMULQDQ / AVX2 / AVX-512.
  - Виміряно (Ryzen 9 3950X, 4MiB×50 разів): scalar 1003 MiB/s, pclmulqdq
    1916 MiB/s (1.91x), **avx2 22531 MiB/s (22.46x)**. AVX-512 виміряти
    неможливо, оскільки він відсутній.
    → **Згодом з'ясувалося, що при повторних вимірюваннях цей коефіцієнт avx2
    коливається в діапазоні 11,6–18,1 раза** (оскільки SIMD-сторона впирається
    в пропускну здатність пам'яті; нормативними є актуальні числа й діапазон з
    розділу «Виміряні бенчмарки» в README.md).
  - `cargo test --release`: усі 11 тестів + 1 doctest проходять. Підтверджено,
    що реалізація PCLMULQDQ збігається зі скалярною для всіх 256 коефіцієнтів.
  - Досвід інтеграції: вбудовано за path-залежністю в `open-raid-z` (заміна
    операцій GF) та `open-english/server` (ендпойнт `/v1/cpu-runtime` і журнал
    запуску).

- **2026-08-22 (продовження) цикл підвищення практичності + функція
  самопредставлення**:
  після початкової реалізації було проведено цикл розробка→TEST→виправлення
  для підвищення інтегровності та практичності.
  - **Цикл 1: додавання API методу Горнера** (`gf_mul_pow2_xor` /
    `gf_mul2_xor` / `gf_mul4_xor`, AVX2 + скалярна). Завдяки цьому шлях AVX2 у
    `mul2_xor_into` / `mul4_xor_into` в `open-raid-z` теж вдалося делегувати до
    open-cpu і ще сильніше скоротити там x86-код. До `gf_xor` також додано
    шлях AVX2 (щоб делегування не призвело до регресії продуктивності).
  - **Цикл 2: покращення зручності використання**. До `CpuCapabilities` додано
    реалізацію `Display` та `has_all()`. Додано `raid6_parity3()`, що виконує
    пакетний розрахунок P/Q/R, який відповідає RAID-Z3. До `examples/bench.rs`
    додано вимірювання XOR і методу Горнера.
  - **Перевірка**: `cargo test --release` — **усі 15 тестів + 2 doctest
    проходять**. Бенчмарк запускався 4 рази поспіль, і розкид (коливання
    11,6–18,1 раза через те, що SIMD-сторона впирається в пропускну здатність
    пам'яті) чесно записано в README у вигляді діапазону.
  - **Реальний баг, знайдений під час інтеграції в `open-english` (важливий
    урок)**: функцію відповіді-самопредставлення на запитання «хто це створив»
    було реалізовано через часткий збіг за ключовим словом (`"誰が作"`), і
    **під час тестування в реальному браузері з'ясувалося, що фраза
    «誰が【このシステムを】作ったのですか?» не виявляється** (бо між
    питальним словом і дієсловом вставлено слова). Виправлено так, щоб список
    питальних слів і список дієслів перевірялися окремо за умовою AND;
    проведено перевірку на 10 позитивних і 6 негативних прикладах, а також
    E2E-перевірку в реальному браузері. Це запис про те, що **такий баг
    знаходиться не тоді, коли «модульні тести пройшли», а лише якщо справді
    ввести фразу в чат**.

- **Що робити далі**:
  1. Поступово інтегрувати також в область контрольних сум і стиснення в
     `aruaru-db`, матричні операції в `aruaru-llm` та відкат на CPU в
     `open-cuda` (наразі лише 2 випадки: `open-raid-z` і `open-english`).
  2. Коли вдасться отримати або забезпечити машину з AVX-512, перевірити шлях
     AVX-512 вимірюваннями і зняти обмеження opt-in.
  3. Для наборів інструкцій, які лише виявляються, але не мають реалізації
     (POPCNT/BMI/FMA/AES-NI/SHA-NI), додавати реалізації операцій у міру того,
     як вони реально знадобляться на стороні залежних проєктів. Зокрема, для
     контрольних сум у `aruaru-db` кандидатом є CRC32C на PCLMULQDQ, а для
     `aruaru-llm` — int8-скалярний добуток на AVX-VNNI/AVX-512 VNNI.
  4. Оскільки збірку побудовано на path-залежності (`path = "../open-cpu"`),
     при збиранні в середовищах без компонування `F:\runo` (наприклад, на VPS)
     знадобиться перехід на git-залежність. Зайнятися цим, коли справа реально
     дійде до збирання на VPS.
  5. Реалізації для CPU лише з SSE2 немає, тож `open-raid-z` зберігає власну
     реалізацію лише для шляху SSE2. Якщо додати версію SSE2, то й її можна
     буде делегувати.
  6. `gf_xor` навіть за SIMD-реалізації дає лише 1,12–1,25 раза відносно
     скалярної (упор у пропускну здатність пам'яті). Можливо, спрацює
     оптимізація з нетимчасовими збереженнями (`_mm256_stream_si256`), що
     уникають забруднення кешу; це варто спробувати для великих буферів
     (не перевірено).
