# PORTING.md — روش مهاجرت از مخازن دیگر به `open-cpu`

روش مهاجرت برای تجمیع کدهای تشخیص قابلیت‌های CPU و کدهای محاسبات GF(2^8) که
`open-raid-z` / `aruaru-db` / `aruaru-llm` / `open-cuda` و دیگران جداگانه
دارند، در `open-cpu`.

## ۰. پیش‌فرض‌ها

`open-cpu` یک **crate کتابخانه‌ای** است، نه سرویس مقیم. نیازی به ارتباط
بین‌فرایندی یا راه‌اندازی فرایند جداگانه نیست؛ کافی است وابستگی را به
`Cargo.toml` اضافه کنید و توابع را فرا بخوانید.

## ۱. افزودن وابستگی

زیر درایو کاری محلی `F:\runo`، وابستگی path ساده‌ترین راه است:

```toml
[dependencies]
open-cpu = { path = "../open-cpu" }
```

اگر از یک crate عضو داخل workspace استفاده می‌کنید، بهتر است در `Cargo.toml`
ریشهٔ workspace بنویسید

```toml
[workspace.dependencies]
open-cpu = { path = "../open-cpu" }
```

و در سمت عضو `open-cpu = { workspace = true }` قرار دهید.

اگر در آینده به وابستگی git تغییر دهید:

```toml
open-cpu = { git = "https://github.com/aon-co-jp/open-cpu", branch = "main" }
```

نام crate با خط تیره `open-cpu` است و مسیر ارجاع از داخل Rust با زیرخط
`open_cpu`.

## ۲. جایگزینی کد تشخیص قابلیت‌های CPU

پیش از مهاجرت (الگوی رایج در مخازن مختلف):

```rust
static HAS_AVX2: OnceLock<bool> = OnceLock::new();
fn has_avx2() -> bool {
    *HAS_AVX2.get_or_init(|| is_x86_feature_detected!("avx2"))
}
```

پس از مهاجرت:

```rust
if open_cpu::detect().avx2 { /* ... */ }
```

`detect()` در داخل خود کش `OnceLock` دارد، پس لازم نیست سمت فراخوان دوباره کش
کنید. چون `&'static CpuCapabilities` برمی‌گرداند، تخصیص حافظه هم رخ نمی‌دهد.

فیلدهای در دسترس: `avx2` `avx512f` `avx512bw` `avx512vl` `pclmulqdq`
`bmi1` `bmi2` `fma` `aes` `popcnt` `sha` `sse2` `ssse3` `avx_vnni` `avx512vnni`.

## ۳. جایگزینی محاسبات GF(2^8) / توازن (عمدتاً `open-raid-z`)

چندجمله‌ای تحویل‌ناپذیر `open-cpu` برابر `0x11d` و مولد `g = 2` است، همانند
Linux md/RAID6 و ZFS RAID-Z. **پیش از مهاجرت حتماً بررسی کنید که چندجمله‌ای و
مولد مخزن خودتان با این‌ها یکی باشد.** اگر متفاوت باشند، مقادیر نخواهند خواند.

| شکل رایج پیش از مهاجرت | پس از مهاجرت |
|---|---|
| `for i in .. { p[i] ^= d[i] }` | `open_cpu::gf_xor(&mut p, &d)` |
| `for i in .. { q[i] ^= gf_mul(d[i], c) }` | `open_cpu::gf_mul_parity(&mut q, &d, c)` |
| `for i in .. { acc[i] = mul2(acc[i]) ^ d[i] }` | `open_cpu::gf_mul2_xor(&mut acc, &d)` |
| `for i in .. { acc[i] = mul4(acc[i]) ^ d[i] }` | `open_cpu::gf_mul4_xor(&mut acc, &d)` |
| روش هورنر با `×2^n` به تعداد دفعات دلخواه | `open_cpu::gf_mul_pow2_xor(&mut acc, &d, n)` |
| `gf_mul(a: u8, b: u8) -> u8` اختصاصی | `open_cpu::gf_mul(a, b)` (`const fn`) |
| `mul2_byte(b) -> u8` اختصاصی | `open_cpu::gf_mul2_byte(b)` (`const fn`) |
| محاسبهٔ اختصاصی ضریب `g^i` | `open_cpu::raid6_coeff(i)` |
| محاسبهٔ یکجای P/Q | `open_cpu::raid6_parity(&stripes, &mut p, &mut q)` |
| محاسبهٔ یکجای P/Q/R (معادل RAID-Z3) | `open_cpu::raid6_parity3(&stripes, &mut p, &mut q, &mut r)` |

`gf_mul_parity` / `gf_xor` وقتی `dst.len() != src.len()` باشد panic می‌کنند.
سمت فراخوان باید طول stripeها را هم‌اندازه کند.

اگر می‌خواهید صریحاً پیاده‌سازی خاصی را فرا بخوانید (برای بنچمارک یا
راستی‌آزمایی):

- `open_cpu::gf_mul_parity_scalar(...)` / `gf_xor_scalar(...)` /
  `gf_mul_pow2_xor_scalar(...)` — safe
- `unsafe { open_cpu::gf_mul_parity_avx2(...) }` — فراخوان‌کننده پشتیبانی AVX2 را
  تضمین می‌کند
- `unsafe { open_cpu::gf_mul_parity_pclmul(...) }` — همان برای SSSE3+PCLMULQDQ
- `unsafe { open_cpu::gf_mul_parity_avx512(...) }` — **اجرا راستی‌آزمایی نشده**

## ۴. راستی‌آزمایی پس از مهاجرت (الزامی)

۱. `cargo build` — حل وابستگی و بیلد باید موفق باشد.
۲. `cargo test` — **همهٔ تست‌های موجود باید قبول شوند**. به‌ویژه باید تأیید شود
   که رشتهٔ بایتی توازن پیش و پس از جایگزینی کاملاً یکسان است. اگر در تست‌های
   موجود مقایسهٔ مقادیر توازن نیست، هنگام مهاجرت افزوده شود.
۳. اگر یک خط `open_cpu::runtime_summary()` در لاگ چاپ کنید، بعداً می‌توان
   فهمید روی سخت‌افزار واقعی کدام پیاده‌سازی انتخاب شده است.

## ۴٫۵ نمونهٔ واقعی مهاجرت (`open-raid-z`، 2026-08-22)

به عنوان مرجع، نکات کلیدی نخستین نمونهٔ مهاجرت:

- `std::is_x86_feature_detected!` داخل `detect_level()` با ارجاع به
  `open_cpu::detect()` جایگزین شد (نوع شمارشی `SimdLevel` که خاص همان مخزن است
  همان‌طور باقی ماند و فقط **مبنای تصمیم‌گیری** آن به open-cpu منتقل شد).
  بدین ترتیب هیچ تغییری در کد فراخوانِ موجود لازم نشد.
- تنها **مسیر AVX2** در `gf_mul_xor_into()` / `xor_into()` /
  `mul_pow2_xor_into()` به open-cpu واگذار شد؛ مسیر AVX-512 (که در سمت
  open-cpu نیز راستی‌آزمایی نشده) و مسیر SSE2 (که در open-cpu پیاده‌سازی ندارد)
  با پیاده‌سازی خود مخزن باقی ماندند. تصمیم این بود که **جایگزینی‌ای که کارایی
  را پایین بیاورد انجام نشود**.
- کرنل‌های SIMD که دیگر استفاده نمی‌شدند حذف نشدند، بلکه با
  `#[allow(dead_code)]` بر جای ماندند تا در آینده مرجعی برای راستی‌آزمایی
  متقابل با سمت open-cpu باشند.

این شیوه توصیه می‌شود: «همه‌چیز را یکجا جایگزین نکنید، بلکه از بخش‌هایی که
هم‌ارزند و کارایی را کاهش نمی‌دهند به‌تدریج واگذار کنید».

## ۵. نکات

- **مسیر AVX-512 از نظر اجرا راستی‌آزمایی نشده است** (ماشین توسعه آن را ندارد).
  چون به صورت پیش‌فرض انتخاب نمی‌شود، مهاجرت رفتار را تغییر نمی‌دهد. تنها هنگام
  راستی‌آزمایی روی ماشین دارای AVX-512، مقدار `OPEN_CPU_ENABLE_AVX512=1` تنظیم
  شود.
- POPCNT/BMI/FMA/AES-NI/SHA-NI/VNNI **فقط تشخیص داده می‌شوند**. پیاده‌سازی
  checksum، فشرده‌سازی یا محاسبات ماتریسی با استفاده از آن‌ها هنوز در `open-cpu`
  نیست، بنابراین کد متناظر در سمت `aruaru-db` / `aruaru-llm` هنوز قابل مهاجرت
  نیست (مهاجرت زودهنگام فقط بخش تشخیص ممکن است).
- خارج از x86 (مانند ARM) همهٔ قابلیت‌ها `false` می‌شوند و اجرا به پیاده‌سازی
  اسکالر می‌افتد. بیلد متقاطع موفق است، اما بهینه‌سازی‌هایی مانند NEON پشتیبانی
  نمی‌شوند.
