# open-cpu

**مكتبة كشف مجموعات تعليمات المعالج والتوزيع (dispatch) في وقت التشغيل** (Rust)،
مشتركة على مستوى منظومة `aon-co-jp` بأكملها.

أُنشئت لتفادي التكرار الناتج عن كتابة `open-raid-z` / `aruaru-db` / `aruaru-llm` /
`open-cuda` لشيفرة كشف قدرات المعالج كلٌّ على حدة.

**ليست خدمة مقيمة (daemon).** إنها حزمة (crate) مكتبية عادية يضيفها كل مستودع
إلى `[dependencies]` في `Cargo.toml` وتُربط داخل العملية نفسها.

## ما تستطيع فعله

1. **كشف قدرات المعالج في وقت التشغيل** — تُعيد `open_cpu::detect()` القيمة
   `&'static CpuCapabilities`. تستخدم `std::is_x86_feature_detected!` وتخزّن
   نتيجة الكشف الأول في `OnceLock`، لذا تكاد تكون تكلفة الاستدعاءات المتكررة
   صفرًا.
2. **توزيع عمليات RAID6 GF(2^8) في وقت التشغيل** — بحسب نتيجة الكشف يُختار في
   وقت التشغيل التنفيذ العددي (scalar) أو PCLMULQDQ أو AVX2 أو AVX-512.

## طريقة الاستخدام

```toml
# 依存側の Cargo.toml
[dependencies]
open-cpu = { path = "../open-cpu" }
```

```rust
// 1. CPU 機能検出
let caps = open_cpu::detect();
println!("{}", caps);   // Display 実装あり
// => sse2 ssse3 popcnt aes pclmulqdq bmi1 bmi2 fma sha avx2

if caps.avx2 { /* ... */ }
if caps.has_all(&[caps.avx2, caps.fma]) { /* AVX2+FMA3 の経路 */ }

// 2. RAID6 パリティ(係数テーブル方式)
let d0 = vec![1u8; 4096];
let d1 = vec![2u8; 4096];
let mut p = vec![0u8; 4096];
let mut q = vec![0u8; 4096];
open_cpu::raid6_parity(&[&d0, &d1], &mut p, &mut q);

// 3. RAID-Z3 相当の P/Q/R(ホーナー法、係数テーブル不要で高速)
let mut r = vec![0u8; 4096];
open_cpu::raid6_parity3(&[&d0, &d1], &mut p, &mut q, &mut r);

// 個別 API
open_cpu::gf_xor(&mut p, &d0);                 // p ^= d0          (P パリティ)
open_cpu::gf_mul_parity(&mut q, &d0, 0x02);    // q ^= d0 * 0x02   (Q パリティ)
open_cpu::gf_mul2_xor(&mut q, &d0);            // q = q*2 ^ d0     (ホーナー法)
open_cpu::gf_mul4_xor(&mut r, &d0);            // r = r*4 ^ d0     (ホーナー法)

// ログ 1 行サマリ
println!("{}", open_cpu::runtime_summary());
// => open-cpu 0.1.0 | features: ... | gf impl: Avx2
```

### قائمة واجهات API العامة

| API | المحتوى | التوزيع |
|---|---|---|
| `detect() -> &'static CpuCapabilities` | كشف قدرات المعالج (تخزين مؤقت عبر `OnceLock`) | — |
| `runtime_summary() -> String` | ملخص من سطر واحد لنتيجة الكشف + التنفيذ المختار | — |
| `selected_impl() -> GfImpl` | التنفيذ المختار لعمليات GF | — |
| `gf_xor(dst, src)` | `dst ^= src` (تكافؤ P) | AVX2 / عددي |
| `gf_mul_parity(dst, src, factor)` | `dst ^= src * factor` (تكافؤ Q) | AVX-512 (opt-in) / AVX2 / PCLMULQDQ / عددي |
| `gf_mul_pow2_xor(acc, src, times)` | `acc = acc * 2^times ^ src` | AVX2 / عددي |
| `gf_mul2_xor` / `gf_mul4_xor` | ما سبق بقيمة `times=1` / `times=2` | كما سبق |
| `raid6_parity(stripes, p, q)` | حساب P/Q دفعةً واحدة بأسلوب جدول المعاملات | حسب ما سبق |
| `raid6_parity3(stripes, p, q, r)` | حساب P/Q/R دفعةً واحدة بطريقة هورنر | حسب ما سبق |
| `gf_mul(a, b) -> u8` | ضرب GF لبايت واحد (`const fn`) | — |
| `gf_mul2_byte(b) -> u8` | مضاعفة بايت واحد فوق GF (`const fn`) | — |
| `raid6_coeff(i) -> u8` | معامل RAID6 وهو `g^i` (`g = 2`) | — |

كما تُنشر نسخ `*_scalar` / `*_avx2` / `*_pclmul` / `*_avx512` التي تستدعي كل
تنفيذ صراحةً (لأغراض القياس والتحقق المتبادل؛ نسخ SIMD هي `unsafe`).

## مجموعات التعليمات المستهدفة بالكشف

| مجموعة التعليمات | الكشف | الاستخدام داخل هذه الحزمة |
|---|---|---|
| SSE2 | ✅ | تُستخدم كمساعد لمسار PCLMULQDQ |
| SSSE3 | ✅ | `pshufb` (الاختزال في مسار PCLMULQDQ) |
| PCLMULQDQ | ✅ | ضرب GF(2^8) (تنفيذ الضرب بلا حمل) |
| AVX2 | ✅ | ضرب GF(2^8) (`vpshufb` split-table، وهو الاختيار الافتراضي) |
| AVX-512F / BW / VL | ✅ | يوجد مسار لضرب GF(2^8) (**غير مُتحقَّق منه بالتشغيل**، انظر أدناه) |
| POPCNT | ✅ | كشف فقط (لا يوجد تنفيذ يستخدمه) |
| BMI1 / BMI2 | ✅ | كشف فقط (لا يوجد تنفيذ يستخدمه) |
| FMA3 | ✅ | كشف فقط (لا يوجد تنفيذ يستخدمه) |
| AES-NI | ✅ | كشف فقط (لا يوجد تنفيذ يستخدمه) |
| SHA-NI | ✅ | كشف فقط (لا يوجد تنفيذ يستخدمه) |
| AVX-VNNI | ✅ | كشف فقط (لاستدلال الذكاء الاصطناعي مستقبلًا، لا يوجد تنفيذ يستخدمه) |
| AVX-512 VNNI | ✅ | كشف فقط (لاستدلال الذكاء الاصطناعي مستقبلًا، لا يوجد تنفيذ يستخدمه) |

في المعماريات غير x86/x86_64 تصبح كل الحقول `false` ويرتد التنفيذ إلى النسخة
العددية (والبناء ينجح).

## تفاصيل تنفيذ GF(2^8)

كثير الحدود غير القابل للاختزال هو `0x11d` (x^8+x^4+x^3+x^2+1)، والمولّد هو
`g = 2`. وهو نفسه المستخدم في Linux md/RAID6 وفي ZFS RAID-Z.

- **العددي**: تنفيذ مرجعي بجدول nibble split (16 مدخلًا × 2).
- **PCLMULQDQ**: عند نشر كل بايت بفواصل 16 بت، لا يفيض حاصل الضرب بلا حمل مع
  معامل من 8 بتات (بحد أقصى 15 بت) إلى الخانة المجاورة. باستغلال هذه الخاصية
  تُضرب 4 بايتات معًا بتعليمة واحدة، ثم تُختزل إلى GF(2^8) بعمليتَي `pshufb`.
  16 byte/iter.
- **AVX2**: تنفيذ split-table باستخدام `vpshufb`. 32 byte/iter.
- **AVX-512F/BW**: نفس split-table بمعالجة 64 byte/iter.

## قياس الأداء الفعلي

`cargo run --release --example bench` (4 MiB × 50 مرة = 200 MiB، factor=0x8d)

جهاز التطوير: **AMD Ryzen 9 3950X** / Windows 11 / rustc 1.96.0

```
open-cpu 0.1.0 | features: sse2 ssse3 popcnt aes pclmulqdq bmi1 bmi2 fma sha avx2 | gf impl: Avx2
scalar   :  207.5 ms     963 MiB/s
pclmulqdq:  109.0 ms    1835 MiB/s  (1.90x vs scalar)
avx2     :   11.4 ms   17473 MiB/s  (18.14x vs scalar)
avx512   : このCPUでは未搭載のため実測不可(未検証)

xor scalar     :  11.5 ms   17451 MiB/s
xor dispatch   :   9.7 ms   20616 MiB/s  (1.15〜1.25x vs scalar)

horner scalar  :  51.5 ms    3880 MiB/s
horner dispatch:  14.8 ms   13521 MiB/s  (2.70〜3.52x vs scalar)
```

**حول تشتت القيم المقيسة (تسجيل صادق)**: عند تنفيذ القياس أربع مرات متتالية،
تفاوتت نسبة تسريع AVX2 لضرب GF ضمن **11.6 إلى 18.1 ضعفًا**، وطريقة هورنر ضمن
**2.70 إلى 3.52 ضعفًا**، وXOR ضمن **1.12 إلى 1.25 ضعفًا** (بينما ظل الجانب
العددي مستقرًا حول 207 ms). يبلغ جانب SIMD ما بين 10000 و20000 MiB/s وبالتالي
فهو **محكوم بعرض نطاق الذاكرة**، ويتأثر بسهولة بحالة الذاكرة المخبأة وبالعمليات
الأخرى. الجدول أعلاه مجرد نتيجة تنفيذ واحد كما هي، والأدق هو فهم نسب التسريع
كنطاقات.

- **ضرب GF(2^8) بمعامل اختياري أسرع 11.6 إلى 18.1 ضعفًا مع AVX2 مقارنةً بالعددي
  (مقيس)**. وهو فعّال في مسار تكافؤ Q ومسار الاستعادة في RAID6.
- **طريقة هورنر أسرع 2.70 إلى 3.52 ضعفًا (مقيس)**. ولأن النسخة العددية مُحسَّنة
  أصلًا بحِيَل البتات على u64، لا يظهر فارق بحجم فارق ضرب GF.
- **XOR البسيط أسرع 1.12 إلى 1.25 ضعفًا**. فالنسخة العددية (u64) ملتصقة أصلًا
  بعرض نطاق الذاكرة، لذا هامش التحسين بـ SIMD ضئيل (كما هو متوقع).
- أما PCLMULQDQ فنسبته 1.90، ولا معنى له إلا **كبديل احتياطي للمعالجات القديمة
  التي لا تدعم AVX2**.

## حالة التحقق (إفصاح صادق)

- ✅ **العددي / PCLMULQDQ / AVX2**: تم التحقق منها بالتشغيل على جهاز التطوير
  المذكور أعلاه. في `cargo test` تم التأكد من صحة التنفيذ العددي بالقياس إلى
  تنفيذ ساذج قائم على إزاحة البتات، ثم التأكد من تطابق مخرجات تنفيذ PCLMULQDQ
  (**جميع المعاملات الـ 256 × 9 أطوال**) وتنفيذ AVX2 (8 معاملات × 11 طولًا،
  بما في ذلك معالجة البواقي) مع التنفيذ العددي. اجتازت جميع الاختبارات الـ 15
  إضافةً إلى doctest اثنين.
- ⚠️ **مسار AVX-512 غير مُتحقَّق منه بالتشغيل**. فلأن جهاز التطوير
  (Ryzen 9 3950X) لا يحتوي على AVX-512، لم يُتحقق إلا من **نجاح الترجمة فقط**.
  ولدواعي السلامة لا يُختار في التوزيع الافتراضي، ولا يُفعَّل إلا اختياريًا
  (opt-in) عند ضبط متغير البيئة `OPEN_CPU_ENABLE_AVX512=1`. وسيبقى هذا التعامل
  قائمًا إلى أن يكتمل التحقق على جهاز يدعم AVX-512.
- ⚠️ بالنسبة إلى POPCNT/BMI1/BMI2/FMA/AES-NI/SHA-NI/VNNI **توجد حقول كشف فحسب**،
  ولا يوجد بعد أي تنفيذ حسابي يستخدمها.
