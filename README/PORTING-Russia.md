# PORTING.md — порядок перехода на `open-cpu` из других репозиториев

Порядок миграции, позволяющий собрать в `open-cpu` код определения
возможностей CPU и код операций GF(2^8), которые по отдельности имеются в
`open-raid-z` / `aruaru-db` / `aruaru-llm` / `open-cuda` и др.

## 0. Предпосылки

`open-cpu` — это **библиотечный крейт**, а не резидентный сервис.
Межпроцессное взаимодействие и запуск отдельного процесса не нужны: всё
сводится к добавлению зависимости в `Cargo.toml` и вызову функций.

## 1. Добавление зависимости

Под локальным рабочим диском `F:\runo` проще всего path-зависимость:

```toml
[dependencies]
open-cpu = { path = "../open-cpu" }
```

При использовании из крейта-участника рабочего пространства желательно
написать в `Cargo.toml` корня рабочего пространства

```toml
[workspace.dependencies]
open-cpu = { path = "../open-cpu" }
```

и указать на стороне участника `open-cpu = { workspace = true }`.

При будущем переходе на git-зависимость:

```toml
open-cpu = { git = "https://github.com/aon-co-jp/open-cpu", branch = "main" }
```

Имя крейта — с дефисом, `open-cpu`; путь для обращения из Rust — с
подчёркиванием, `open_cpu`.

## 2. Замена кода определения возможностей CPU

До миграции (типичный для репозиториев шаблон):

```rust
static HAS_AVX2: OnceLock<bool> = OnceLock::new();
fn has_avx2() -> bool {
    *HAS_AVX2.get_or_init(|| is_x86_feature_detected!("avx2"))
}
```

После миграции:

```rust
if open_cpu::detect().avx2 { /* ... */ }
```

`detect()` внутри уже кэширован через `OnceLock`, поэтому кэшировать
дополнительно на стороне вызова не нужно. Так как возвращается
`&'static CpuCapabilities`, аллокация тоже не происходит.

Доступные поля: `avx2` `avx512f` `avx512bw` `avx512vl` `pclmulqdq`
`bmi1` `bmi2` `fma` `aes` `popcnt` `sha` `sse2` `ssse3` `avx_vnni` `avx512vnni`.

## 3. Замена операций GF(2^8) / расчёта чётности (в основном `open-raid-z`)

Неприводимый многочлен в `open-cpu` — `0x11d`, порождающий элемент — `g = 2`,
что совпадает с Linux md/RAID6 и ZFS RAID-Z. **Перед миграцией обязательно
проверьте, совпадают ли с этим многочлен и порождающий элемент в вашем
репозитории.** Если они отличаются, числовые значения перестанут сходиться.

| Типичная форма до миграции | После миграции |
|---|---|
| `for i in .. { p[i] ^= d[i] }` | `open_cpu::gf_xor(&mut p, &d)` |
| `for i in .. { q[i] ^= gf_mul(d[i], c) }` | `open_cpu::gf_mul_parity(&mut q, &d, c)` |
| `for i in .. { acc[i] = mul2(acc[i]) ^ d[i] }` | `open_cpu::gf_mul2_xor(&mut acc, &d)` |
| `for i in .. { acc[i] = mul4(acc[i]) ^ d[i] }` | `open_cpu::gf_mul4_xor(&mut acc, &d)` |
| Метод Горнера с произвольным числом `×2^n` | `open_cpu::gf_mul_pow2_xor(&mut acc, &d, n)` |
| Собственная `gf_mul(a: u8, b: u8) -> u8` | `open_cpu::gf_mul(a, b)` (`const fn`) |
| Собственная `mul2_byte(b) -> u8` | `open_cpu::gf_mul2_byte(b)` (`const fn`) |
| Собственный расчёт коэффициента `g^i` | `open_cpu::raid6_coeff(i)` |
| Пакетный расчёт P/Q | `open_cpu::raid6_parity(&stripes, &mut p, &mut q)` |
| Пакетный расчёт P/Q/R (соответствует RAID-Z3) | `open_cpu::raid6_parity3(&stripes, &mut p, &mut q, &mut r)` |

`gf_mul_parity` / `gf_xor` вызывают panic при `dst.len() != src.len()`.
Выравнивайте длину страйпов на стороне вызова.

Если нужно явно вызвать конкретную реализацию (для бенчмарков или проверки):

- `open_cpu::gf_mul_parity_scalar(...)` / `gf_xor_scalar(...)` /
  `gf_mul_pow2_xor_scalar(...)` — safe
- `unsafe { open_cpu::gf_mul_parity_avx2(...) }` — вызывающая сторона
  гарантирует поддержку AVX2
- `unsafe { open_cpu::gf_mul_parity_pclmul(...) }` — то же для SSSE3+PCLMULQDQ
- `unsafe { open_cpu::gf_mul_parity_avx512(...) }` — **выполнение не проверено**

## 4. Проверка после миграции (обязательно)

1. `cargo build` — разрешение зависимостей и сборка должны проходить.
2. `cargo test` — **все существующие тесты должны проходить**. В частности,
   убедитесь, что байтовые последовательности чётности до и после замены
   полностью совпадают. Если в существующих тестах нет сравнения значений
   чётности, добавьте его при миграции.
3. Если выводить в журнал одну строку `open_cpu::runtime_summary()`, то позже
   можно будет узнать, какая реализация была выбрана на реальной машине.

## 4.5 Реальный пример миграции (`open-raid-z`, 2026-08-22)

Для справки приведём ключевые моменты первого реального случая миграции:

- `std::is_x86_feature_detected!` внутри `detect_level()` заменён на обращение
  к `open_cpu::detect()` (специфичное для репозитория перечисление
  `SimdLevel` оставлено как есть, в open-cpu перенесены **только исходные
  данные для его определения**). Благодаря этому существующие вызывающие
  стороны не пришлось менять вовсе.
- В `gf_mul_xor_into()` / `xor_into()` / `mul_pow2_xor_into()` в open-cpu
  делегирован **только путь AVX2**, а путь AVX-512 (в open-cpu он тоже не
  проверен) и путь SSE2 (в open-cpu реализации нет) оставлены с реализацией
  на стороне репозитория. Решение принято по принципу **не выполнять замену,
  которая снижает производительность**.
- Переставшие использоваться SIMD-ядра не удалены, а оставлены с пометкой
  `#[allow(dead_code)]` как эталон для будущей взаимной проверки со стороной
  open-cpu.

Рекомендуется именно такой подход: «не заменять всё сразу, а поэтапно
делегировать начиная с тех частей, которые эквивалентны и не теряют в
производительности».

## 5. Замечания

- **Путь AVX-512 не проверен выполнением** (на машине разработки его нет).
  По умолчанию он не выбирается, поэтому миграция не изменит поведение. Задавайте
  `OPEN_CPU_ENABLE_AVX512=1` только при проверке на машине с AVX-512.
- POPCNT/BMI/FMA/AES-NI/SHA-NI/VNNI — **только определение**. Реализаций
  контрольных сумм, сжатия и матричных операций с их использованием в
  `open-cpu` ещё нет, поэтому соответствующий код на стороне `aruaru-db` /
  `aruaru-llm` пока мигрировать нельзя (перенести заранее только часть с
  определением возможно).
- Вне x86 (ARM и т. п.) все возможности становятся `false` и происходит откат
  к скалярной реализации. Кросс-сборка проходит, но оптимизации вроде NEON не
  поддерживаются.
