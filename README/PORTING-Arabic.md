# PORTING.md — خطوات الانتقال من المستودعات الأخرى إلى `open-cpu`

خطوات الترحيل اللازمة لتجميع شيفرة كشف قدرات المعالج وشيفرة عمليات GF(2^8)
التي يملكها كلٌّ من `open-raid-z` / `aruaru-db` / `aruaru-llm` / `open-cuda`
على حدة، ضمن `open-cpu`.

## 0. المقدمات

`open-cpu` هي **حزمة (crate) مكتبية** وليست خدمة مقيمة. فلا حاجة إلى اتصال بين
العمليات ولا إلى تشغيل عملية منفصلة، بل يكتمل الأمر بمجرد إضافة الاعتماد في
`Cargo.toml` واستدعاء الدوال.

## 1. إضافة الاعتماد

تحت قرص العمل المحلي `F:\runo`، يكون الاعتماد بـ path هو الأسهل:

```toml
[dependencies]
open-cpu = { path = "../open-cpu" }
```

وعند الاستخدام من حزمة عضو داخل مساحة عمل (workspace)، يُفضَّل أن يُكتب في
`Cargo.toml` الخاص بجذر مساحة العمل:

```toml
[workspace.dependencies]
open-cpu = { path = "../open-cpu" }
```

ثم يُكتب في جانب العضو `open-cpu = { workspace = true }`.

وعند التحويل مستقبلًا إلى اعتماد git:

```toml
open-cpu = { git = "https://github.com/aon-co-jp/open-cpu", branch = "main" }
```

اسم الحزمة بالشرطة `open-cpu`، أما المسار المستخدم عند الإشارة إليها من Rust
فبالشرطة السفلية `open_cpu`.

## 2. استبدال شيفرة كشف قدرات المعالج

قبل الترحيل (نمط شائع في كل مستودع):

```rust
static HAS_AVX2: OnceLock<bool> = OnceLock::new();
fn has_avx2() -> bool {
    *HAS_AVX2.get_or_init(|| is_x86_feature_detected!("avx2"))
}
```

بعد الترحيل:

```rust
if open_cpu::detect().avx2 { /* ... */ }
```

`detect()` مخزَّنة داخليًا في ذاكرة مؤقتة عبر `OnceLock`، فلا حاجة إلى تخزين
مؤقت إضافي في جانب المستدعي. ولأنها تُعيد `&'static CpuCapabilities` فلا يحدث
أي تخصيص للذاكرة.

الحقول المتاحة: `avx2` `avx512f` `avx512bw` `avx512vl` `pclmulqdq`
`bmi1` `bmi2` `fma` `aes` `popcnt` `sha` `sse2` `ssse3` `avx_vnni` `avx512vnni`.

## 3. استبدال عمليات GF(2^8) / التكافؤ (في `open-raid-z` أساسًا)

كثير الحدود غير القابل للاختزال في `open-cpu` هو `0x11d`، والمولّد `g = 2`،
وهو نفسه المستخدم في Linux md/RAID6 وفي ZFS RAID-Z. **قبل الترحيل يجب التأكد من
تطابق كثير الحدود والمولّد في مستودعك مع هذين.** فإن اختلفا لن تتطابق القيم.

| الشكل الشائع قبل الترحيل | بعد الترحيل |
|---|---|
| `for i in .. { p[i] ^= d[i] }` | `open_cpu::gf_xor(&mut p, &d)` |
| `for i in .. { q[i] ^= gf_mul(d[i], c) }` | `open_cpu::gf_mul_parity(&mut q, &d, c)` |
| `for i in .. { acc[i] = mul2(acc[i]) ^ d[i] }` | `open_cpu::gf_mul2_xor(&mut acc, &d)` |
| `for i in .. { acc[i] = mul4(acc[i]) ^ d[i] }` | `open_cpu::gf_mul4_xor(&mut acc, &d)` |
| طريقة هورنر بـ `×2^n` لعدد اختياري من المرات | `open_cpu::gf_mul_pow2_xor(&mut acc, &d, n)` |
| دالة خاصة `gf_mul(a: u8, b: u8) -> u8` | `open_cpu::gf_mul(a, b)` (`const fn`) |
| دالة خاصة `mul2_byte(b) -> u8` | `open_cpu::gf_mul2_byte(b)` (`const fn`) |
| حساب خاص للمعامل `g^i` | `open_cpu::raid6_coeff(i)` |
| حساب P/Q دفعةً واحدة | `open_cpu::raid6_parity(&stripes, &mut p, &mut q)` |
| حساب P/Q/R دفعةً واحدة (بما يعادل RAID-Z3) | `open_cpu::raid6_parity3(&stripes, &mut p, &mut q, &mut r)` |

تُحدث `gf_mul_parity` / `gf_xor` حالة panic عند `dst.len() != src.len()`.
فيجب على جانب المستدعي توحيد أطوال الشرائح مسبقًا.

وعند الرغبة في استدعاء تنفيذ معيّن صراحةً (لأغراض القياس أو التحقق):

- `open_cpu::gf_mul_parity_scalar(...)` / `gf_xor_scalar(...)` /
  `gf_mul_pow2_xor_scalar(...)` — safe
- `unsafe { open_cpu::gf_mul_parity_avx2(...) }` — المستدعي يضمن دعم AVX2
- `unsafe { open_cpu::gf_mul_parity_pclmul(...) }` — كذلك SSSE3+PCLMULQDQ
- `unsafe { open_cpu::gf_mul_parity_avx512(...) }` — **غير مُتحقَّق منه بالتشغيل**

## 4. التحقق بعد الترحيل (إلزامي)

1. `cargo build` — أن يمر حل الاعتمادات والبناء بنجاح.
2. `cargo test` — **أن تجتاز جميع الاختبارات القائمة**. وعلى وجه الخصوص، يُتحقق
   من أن سلسلة بايتات التكافؤ متطابقة تمامًا قبل الاستبدال وبعده. وإن لم تكن
   الاختبارات القائمة تتضمن مقارنة قيم التكافؤ، فتُضاف عند الترحيل.
3. إخراج سطر واحد من `open_cpu::runtime_summary()` في السجل يتيح التحقق لاحقًا
   من أي تنفيذ اختير على الجهاز الفعلي.

## 4.5 مثال ترحيل فعلي (`open-raid-z`، 2026-08-22)

للمرجعية، إليك أبرز نقاط أول مثال ترحيل فعلي:

- استُبدل `std::is_x86_feature_detected!` داخل `detect_level()` بمرجع إلى
  `open_cpu::detect()` (أُبقي التعداد الخاص بالمستودع `SimdLevel` كما هو،
  ونُقلت إلى open-cpu **مادة الحكم فقط**). وبهذا لم يلزم تغيير أي شيء في جانب
  المستدعين القائمين.
- فُوِّض إلى open-cpu **مسار AVX2 فقط** في `gf_mul_xor_into()` / `xor_into()` /
  `mul_pow2_xor_into()`، بينما أُبقي على تنفيذ المستودع لمسار AVX-512 (غير
  مُتحقَّق منه في جانب open-cpu أيضًا) ومسار SSE2 (لا يوجد له تنفيذ في
  open-cpu). وهو قرار مبني على مبدأ **عدم إجراء استبدال يخفض الأداء**.
- لم تُحذف أنوية SIMD التي لم تعد مستخدمة، بل بقيت مع وضع `#[allow(dead_code)]`
  عليها، لتكون مرجعًا عند التحقق المتبادل مستقبلًا مع جانب open-cpu.

ويُوصى بهذا النهج القائم على «عدم استبدال كل شيء دفعةً واحدة، بل التفويض
تدريجيًا ابتداءً من الأجزاء المكافئة التي لا ينخفض فيها الأداء».

## 5. نقاط انتباه

- **مسار AVX-512 غير مُتحقَّق منه بالتشغيل** (جهاز التطوير لا يدعمه). ولأنه لا
  يُختار افتراضيًا، فلن يتغير السلوك بسبب الترحيل. ولا يُضبط
  `OPEN_CPU_ENABLE_AVX512=1` إلا عند التحقق على جهاز يدعم AVX-512.
- بالنسبة إلى POPCNT/BMI/FMA/AES-NI/SHA-NI/VNNI فهي **كشف فقط**. ولأن تنفيذات
  المجاميع الاختبارية والضغط وعمليات المصفوفات التي تستخدمها ليست موجودة بعد في
  `open-cpu`، فإن الشيفرة المعنية في جانب `aruaru-db` / `aruaru-llm` لا يمكن
  ترحيلها بعد (وإن كان ممكنًا ترحيل جزء الكشف وحده أولًا).
- في غير x86 (مثل ARM) تصبح كل الميزات `false` ويرتد التنفيذ إلى النسخة العددية.
  والبناء المتقاطع يمر بنجاح، لكن التحسينات مثل NEON غير مدعومة.
