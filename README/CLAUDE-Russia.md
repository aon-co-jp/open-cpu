# Политика разработки и правила среды разработки (open-cpu)

Этот репозиторий — часть экосистемы `aon-co-jp`. **Нормативным источником для
общих для всех репозиториев принципов проектирования и правил эксплуатации
(тщательная проверка, запрет преувеличенных отчётов, отказ от изобретения
велосипеда, автоматическое продолжение без запроса подтверждения и т. д.)
является [`open-raid-z/CLAUDE.md`](https://github.com/aon-co-jp/open-raid-z/blob/main/CLAUDE.md).**
Здесь они не дублируются; описываются только вопросы, специфичные для этого
репозитория.

Рабочий диск — `F:\runo\open-cpu` (новая раскладка).

## Роль этого репозитория

Создан как общая основа, потому что `open-raid-z` / `aruaru-db` / `aruaru-llm` /
`open-cuda` собирались **каждый по-своему** реализовывать определение во время
выполнения и диспетчеризацию наборов инструкций CPU
(AVX2/AVX-512/PCLMULQDQ/BMI1/BMI2/FMA3/AES-NI/POPCNT/SHA-NI).

- **Это библиотечный крейт** (указание пользователя, 2026-08-22). Он не должен
  становиться резидентным сервисом (демоном). Каждый репозиторий добавляет его
  в `[dependencies]` и линкует внутрь того же процесса. Не вводить межпроцессное
  взаимодействие.
- Область действия ограничена «определением возможностей CPU» и
  «диспетчеризацией вычислений на основе результата этого определения». Не
  переносить сюда доменную логику отдельных репозиториев (стратегию
  чередования в RAID, управление страницами в БД, загрузку моделей в LLM
  и т. п.).
- Не увеличивать число зависимых крейтов (сейчас `[dependencies]` пуст,
  только `std`). Это основа, лежащая в самом низу каждого репозитория, поэтому
  привнесённая зависимость распространится на всё.

## Правила реализации и проверки (специфичные для этого репозитория)

- **Добавив SIMD-реализацию, обязательно одновременно пишите тест на
  совпадение выхода со скалярной реализацией.** Обязательно включайте в
  тест-кейсы остаток (длину, не кратную ширине вектора).
- **Пути кода, которые нельзя выполнить на реальной машине, явно помечайте как
  «не проверено» и не давайте выбирать их диспетчеризацией по умолчанию.**
  Сейчас это относится к пути AVX-512 (машина разработки AMD Ryzen 9 3950X не
  имеет AVX-512). Он включается только по opt-in через
  `OPEN_CPU_ENABLE_AVX512=1`. Когда проверка на машине с AVX-512 будет
  завершена, снимите это ограничение и обновите пометки «не проверено» в
  README.md / PORTING.md / этом файле.
- Записывая числа бенчмарков, пишите «измерено» **только о том, что было
  действительно измерено**. Не выдавайте оценочные и теоретические значения за
  измеренные.
- `cargo bench` не используется; достаточно простого измерения через
  `std::time::Instant` в `examples/bench.rs` (чтобы не увеличивать число
  зависимостей).

## HANDOFF

- **2026-08-22 создание с нуля + интеграция в 2 репозитория**:
  начальная реализация создана из состояния пустого репозитория.
  - `src/caps.rs`: структура `CpuCapabilities` и `detect()` (кэш `OnceLock`).
    Объекты определения: avx2 / avx512f / avx512bw / avx512vl / pclmulqdq /
    bmi1 / bmi2 / fma / aes / popcnt / sha / sse2 / ssse3 / avx-vnni /
    avx512vnni.
  - `src/gf.rs`: операции GF(2^8) для RAID6 (многочлен 0x11d, порождающий
    элемент g=2). Публикуются `gf_xor` / `gf_mul_parity` / `raid6_parity` /
    `raid6_coeff`, диспетчеризация во время выполнения между 4 реализациями:
    скалярной / PCLMULQDQ / AVX2 / AVX-512.
  - Измерено (Ryzen 9 3950X, 4MiB×50 раз): scalar 1003 MiB/s, pclmulqdq
    1916 MiB/s (1.91x), **avx2 22531 MiB/s (22.46x)**. AVX-512 измерить
    невозможно, так как он отсутствует.
    → **Позже выяснилось, что при повторных измерениях этот коэффициент avx2
    колеблется в диапазоне 11,6–18,1 раза** (поскольку SIMD-сторона упирается
    в пропускную способность памяти; нормативными являются актуальные числа и
    диапазон из раздела «Измеренные бенчмарки» в README.md).
  - `cargo test --release`: все 11 тестов + 1 doctest проходят. Подтверждено,
    что реализация PCLMULQDQ совпадает со скалярной для всех 256
    коэффициентов.
  - Опыт интеграции: встроен по path-зависимости в `open-raid-z` (замена
    операций GF) и `open-english/server` (эндпойнт `/v1/cpu-runtime` и журнал
    запуска).

- **2026-08-22 (продолжение) цикл повышения практичности + функция
  самопредставления**:
  после начальной реализации был проведён цикл разработка→TEST→исправление для
  повышения интегрируемости и практичности.
  - **Цикл 1: добавление API метода Горнера** (`gf_mul_pow2_xor` /
    `gf_mul2_xor` / `gf_mul4_xor`, AVX2 + скалярная). Благодаря этому путь AVX2
    в `mul2_xor_into` / `mul4_xor_into` в `open-raid-z` тоже удалось
    делегировать в open-cpu и ещё сильнее сократить там x86-код. В `gf_xor`
    также добавлен путь AVX2 (чтобы делегирование не привело к регрессии
    производительности).
  - **Цикл 2: улучшение удобства использования**. В `CpuCapabilities`
    добавлены реализация `Display` и `has_all()`. Добавлена `raid6_parity3()`,
    выполняющая пакетный расчёт P/Q/R, соответствующий RAID-Z3. В
    `examples/bench.rs` добавлены измерения XOR и метода Горнера.
  - **Проверка**: `cargo test --release` — **все 15 тестов + 2 doctest
    проходят**. Бенчмарк запускался 4 раза подряд, и разброс (колебания
    11,6–18,1 раза из-за того, что SIMD-сторона упирается в пропускную
    способность памяти) честно записан в README в виде диапазона.
  - **Реальный баг, найденный при интеграции в `open-english` (важный урок)**:
    функция ответа-самопредставления на вопрос «кто это создал» была
    реализована через частичное совпадение по ключевому слову
    (`"誰が作"`), и **при тестировании в реальном браузере выяснилось, что
    фраза «誰が【このシステムを】作ったのですか?» не определяется** (потому
    что между вопросительным словом и глаголом вставлены слова). Исправлено
    так, чтобы список вопросительных слов и список глаголов проверялись
    отдельно по условию AND; проведена проверка на 10 положительных и 6
    отрицательных примерах, а также E2E-проверка в реальном браузере. Это
    запись о том, что **такой баг находится не тогда, когда «модульные тесты
    прошли», а только если действительно ввести фразу в чат**.

- **Что делать дальше**:
  1. Постепенно интегрировать также в область контрольных сумм и сжатия в
     `aruaru-db`, матричные операции в `aruaru-llm` и откат на CPU в
     `open-cuda` (сейчас только 2 случая: `open-raid-z` и `open-english`).
  2. Когда удастся получить или обеспечить машину с AVX-512, проверить путь
     AVX-512 измерениями и снять ограничение opt-in.
  3. Для наборов инструкций, которые только определяются, но не имеют
     реализации (POPCNT/BMI/FMA/AES-NI/SHA-NI), добавлять реализации операций
     по мере того, как они реально понадобятся на стороне зависимых проектов.
     В частности, для контрольных сумм в `aruaru-db` кандидатом является CRC32C
     на PCLMULQDQ, а для `aruaru-llm` — int8-скалярное произведение на
     AVX-VNNI/AVX-512 VNNI.
  4. Поскольку сборка построена на path-зависимости (`path = "../open-cpu"`),
     при сборке в средах без раскладки `F:\runo` (например, на VPS)
     потребуется переключение на git-зависимость. Заняться этим, когда дело
     реально дойдёт до сборки на VPS.
  5. Реализации для CPU только с SSE2 нет, поэтому `open-raid-z` сохраняет
     собственную реализацию только для пути SSE2. Если добавить версию SSE2,
     то и её можно будет делегировать.
  6. `gf_xor` даже при SIMD-реализации даёт лишь 1,12–1,25 раза относительно
     скалярной (упор в пропускную способность памяти). Возможно, сработает
     оптимизация с невременными сохранениями (`_mm256_stream_si256`),
     избегающими загрязнения кэша; это стоит попробовать для больших буферов
     (не проверено).
